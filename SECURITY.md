# Security

This is a 36-hour hackathon prototype built for the Capital One challenge at HackMTY 2026. It is
not a regulated entity and it holds no real customer data. The policies below are short because
they are meant to be followed under time pressure, not read once.

## Synthetic data only

- **100 percent of the data in this repository and in any demo is synthetic.** It is generated by
  `packages/seed` from a fixed RNG seed. The methodology is documented in `docs/08-data-model.md`.
- **No real personally identifiable information, ever.** Not in code, not in fixtures, not in
  issues, not in pull requests, not in screenshots, not in the demo video, not in the Devpost
  submission. This includes real names, real account numbers, real addresses and real phone numbers,
  including our own.
- Nessie `account_number` values are synthetic and are still treated as sensitive: never log them,
  never screenshot them in full, never paste them into an issue.
- No card primary account numbers are stored anywhere, in any form. There is no PAN in this system.
- `/enterprise/*` on the Nessie API is a world-readable pool shared with every other team at the
  event. Never write anything identifying about this project, this team or this idea into it, and
  never treat anything read from it as our data.

## Secrets and keys

- API keys and connection strings live in `.env` only, which is gitignored. `.env.example` lists
  every variable name with empty values and is the only env file that is committed.
- Secrets are never committed, never echoed into a terminal that is being screenshotted, never
  pasted into an issue or a pull request, and never added to CI. Unit tests must pass with no
  network and no secrets, which is also why CI stays under three minutes.
- Secrets are shared between teammates through the team chat, not through the repository.
- Secret scanning and push protection are enabled on this repository, so a key pasted into a commit
  is blocked at push time rather than discovered after the event.

### If a key leaks

1. **Revoke and rotate it at the provider first.** Do this before anything else and before telling
   anyone. Rotating is always faster than rewriting history and it is always sufficient.
2. Tell the lead (`garzario`) immediately afterwards, in the team channel.
3. Only then decide whether rewriting git history is worth the time. During the event it usually is
   not, because the old key is already dead.
4. Replace the value in every `.env` and in the deploy environment, then run `bun run doctor`.

All event keys are rotated or revoked after 2026-09-13 regardless of whether anything leaked.

## Supply chain

- Exact pins only. Never `@latest`, never a caret range. `bunfig.toml` sets `exact = true`.
- `bunfig.toml` sets `minimumReleaseAge = 259200`, a three-day quarantine on newly published
  versions. A package published in the last three days cannot be installed, on any of the four
  laptops or in CI. **Do not remove or lower this value.** It exists because a compromised release
  is usually caught within days, and because it is a checkable policy rather than a promise.
- The vetted pin table in `CONTRIBUTING.md` is the allowed dependency set. Adding anything outside
  it requires running the age check in that file first.
- `bun install --frozen-lockfile` in CI, so a lockfile that does not match `package.json` fails
  loudly instead of resolving something new on a runner.
- Never `bun pm trust --all`. Postinstall scripts are trusted per package, deliberately, never in
  bulk.
- npm, npx, yarn and pnpm are denied in `.claude/settings.json` and must not be reintroduced.

## Repository hygiene

The pre-public scrub, run before making the repository public and again before the final
submission:

```bash
git log --all -p | grep -nEi '(api[_-]?key|secret|bearer |password|BEGIN .*PRIVATE KEY)' | head -20
git log --all --name-only --pretty=format: | sort -u | grep -E '^\.env' || echo "no .env in history"
grep -rnEi 'co-authored-by|generated with' --include='*.md' . || echo "no attribution in docs"
grep -rn '' .env.example | grep -vE '=$' || echo ".env.example has no values, good"
```

If the first command finds a secret, go to "If a key leaks" above and revoke first.

Also check before the repository goes public or a screenshot is published: no real names other than
the four team members, no other team's data, no `.env` contents, and no personal data in any image
in `assets/`.

## Scope of this policy

There is no production deployment, no real user, no money movement and no regulated activity in
this prototype. The regulatory analysis, including where the boundary would sit if this were
operated for real and which fields would be tokenized, is in `docs/06-regulatory-privacy.md`.

## Reporting

Open an issue with the `type/bug` label for anything that is not itself sensitive. For anything
involving a key, a credential or personal data, message the lead (`garzario`) in the team channel
directly and do not open a public issue.
